# 界面原型渲染流程

改界面（尤其**配色和间距**）之前，先用 HTML 画出版面、渲染成图看一遍，再动 C++ 代码。
文字描述判断不了"哪个更好看"，只有看到图才能定。

配套工具：

| 文件 | 用途 |
|---|---|
| `scripts/render_mock.sh` | 把 HTML 渲染成 PNG（真·2x 视网膜） |
| `scripts/mock_template.html` | 可直接复制的原型模板（以实时天气页为例） |
| `scripts/measure_text.py` | 算字符串的**精确**渲染宽度，用于定死槽位宽度 |

---

## 一、五步流程

```
1. 抄坐标   ── 从页面 .cpp 里把每个元素的 left/top/字号/颜色抄进原型
2. 并排画   ── 把候选方案放在一行里，每个上面写一行说明
3. 渲染     ── ./scripts/render_mock.sh /tmp/mock/x.html
4. 看图     ── 用 read_image 把 PNG 读出来（这一步不能省）
5. 定案     ── 确认后改 C++，再用 measure_text.py --all 复核槽位宽度
```

原型放在 `/tmp/mock/` 下即可 —— 它是**用完即弃的决策工具**，不是交付物，
不需要进仓库。

---

## 二、原型页的四条约定

### 1. 「屏幕」固定 240×320，与设备一致

```css
.screen { width: 240px; height: 320px; position: relative; overflow: hidden; }
```

240×320 就是 `kScreenWidth` / `kScreenHeight`。原型按真实尺寸画，才能看出
"这一行放不放得下"。

### 2. 元素用绝对定位，`left/top` 直接抄 LVGL 的坐标

```js
el('杭州', 74, 262, `font-size:16px; color:${c.text}`);
```

**不要用 flex / grid 排版。** 原型与代码必须是 1:1 的 —— 出了问题时，
"原型里第 3 个元素"能直接对上 `.cpp` 里那一行。用流式布局就失去了这个对应关系。

**每个坐标后面标上它来自哪个常量**，例如：

```js
el('雨', 14, 214, `font-size:44px; color:${WEATHER_RAIN[mode]}`);  // kWeatherX, kBlockTop
el('22℃', 72, 222, `font-size:26px; color:${c.accent}`);           // kTemperatureX, kBlockTop+8
```

这既是给自己核对用的，也让下次改原型的人知道该去代码里对哪一行。

**画完做一次机械校验** —— 把模板里的坐标与代码常量逐项比对，不要靠眼睛看：

```python
src = open('components/pages/real_time_weather_page.cpp').read()
c = {k: int(v) for k, v in re.findall(r'constexpr int (\w+) = (\d+);', src)}
# 然后断言 模板里的 left/top == c['kWeatherX'] 之类
```

### 3. 多个方案并排，每个带说明

```html
<div class="row">   <!-- display:flex -->
  <div class="col"><div class="caption">现状 · 标签 #888</div><div class="screen">…</div></div>
  <div class="col"><div class="caption">方案 A · 标签 #fff</div><div class="screen">…</div></div>
</div>
```

**比较是重点。** 单看一张图判断不出"A 和 B 哪个好"。深浅两个主题也各占一格。

### 4. 配色与字号**从代码里抄**，不要凭记忆写

颜色抄 `components/pages/ui_theme.cpp`，坐标抄对应页面的 `.cpp`。
凭记忆写就会写出代码里根本没有的值，讨论就建立在假前提上（见下文踩坑记录）。

---

## 三、渲染：必须用真·2x

```bash
./scripts/render_mock.sh /tmp/mock/x.html /tmp/mock/x.png 1080x400
# 已渲染: /tmp/mock/x.png  (2160 800)  <- 窗口 1080x400 的 2 倍
```

脚本内部用的是 `--force-device-scale-factor=2`。

**常见的错误做法**：先按 1x 截图，再用 HTML 把 `<img>` 放大到两倍。
那只是插值，边缘照样是糊的 ✗ 设备是 240×320 的小屏、字体只有 16~70px，
**1x 截图里 1 个像素的差别正好是配色和间距的判断依据**，糊掉就白渲染了。

窗口尺寸要显式给：headless 不会自动裁剪到内容大小，给大了留一片背景色、
给小了会截断。

### 渲染完必须真的看图

```
read_image /tmp/mock/x.png
```

"渲染了"不等于"看过了"。脚本只会告诉你文件生成了，不会告诉你**画错了**。

## 四、踩过的坑

每一条都是真实发生过的，直接导致了错误的结论或返工。

| 坑 | 后果 | 正确做法 |
|---|---|---|
| **凭记忆写数值**：原型里写了代码里根本没有的取值 | 讨论建立在假前提上，用户看实机后反问"怎么和图上不一样" | 数值**从代码里抄**。拿不准就先去 `grep` |
| **只改一个角色却动了其它角色**：某方案里把"标签"改成白色时，把底部提示行也一起设成了白色 | 原型**错误代表了方案**，用户按错误的图做判断 | 一个方案只改**它要改的那一处**，其余保持与现状完全一致 |
| **引用不存在的图片**：`<img src="astro.jpg">` 而文件不存在 | 渲染成破图占位符，干扰对版面的判断 | 图片用**色块/边框占位**并注明；或转 base64 内嵌 |
| **1x 截图再放大** | 边缘糊，看不出 1px 级的配色差异 | `--force-device-scale-factor=2` |
| **忘了看渲染结果** | 以为画对了，其实元素叠在一起 | 渲染完立刻 `read_image` |
| **模板本身的坐标靠记忆写** | 天气大字写在 x=92（实为 14），与温度重叠；日期字号写 18px（实为 16px） | 坐标**逐个标注常量名**，画完做一次机械校验 |
| **工具自身的盲区**：`measure_text.py` 只看字库里有没有 `kern_classes` 这个字符串 | 纯汉字子集字库（`.kern_dsc = NULL`）会让它直接崩 —— 而这个工具是"槽位放不放得下"的唯一依据 | 判据要看**三张 kern 表本体是否都存在**，不能只看字符串名 |

## 五、原型的**边界**——它不能替代什么

原型是**决策工具**，不是验收工具。它的坐标系与 LVGL 一致，但排版细节不一致：

| 原型算得准 | 原型算不准 |
|---|---|
| 元素的 `left`/`top`、字号、颜色 | **字符串渲染宽度**（浏览器的字体 ≠ 设备字库） |
| 版面是否放得下（大致） | 具体的像素余量、kerning、逐字形取整 |
| 横向构图 | **纵向留白**：浏览器的 line box 与 LVGL 的 `line_height`／字形 `ofs_y` 不是一回事 |

**纵向是个容易掉进去的坑**：实时天气页的时间在原型里看着"上下居中"，
实机上却明显偏上（上留 20px、下留 47px）。因为原型按 `top:66px` +
浏览器的行高画，而设备按 LVGL 的 `kTimeY=66` + 字库 `line_height=47` 画 ——
**两者对"这一行占多高"的定义不同**。

判断纵向留白要**算**，不要看原型：

```python
上留 = kTimeY - (日期y + 日期line_height)
下留 = 分割线y - (kTimeY + 时间line_height)
# 两者不等就说明没居中；把 kTimeY 挪动 (下留-上留)/2
```

所以**定死槽位宽度时必须用 `measure_text.py`**，它复现的是 LVGL 的真实算法：

```bash
python3 scripts/measure_text.py dida_cn_16 "08-08" "中到大雪" "20/30℃"
python3 scripts/measure_text.py --all     # 复核所有登记在册的槽位
```

原型用于回答"**这样好不好看**"，`measure_text.py` 用于回答"**这样放不放得下**"。
两个问题必须分开问、分别验证。

### 需要判断"间距好不好"时：给原型注入逐字宽度

普通原型里浏览器的字体宽度与设备不同，所以**间距是不准的**。但要讨论
"这个间距合不合适"时，间距恰恰是关键 —— 这时可以给每个字符套一个
`display:inline-block` 的 `<span>`，宽度取 `measure_text.py` 算出的值：

```python
# 从字库读出每个字符的 advance（1/16 px 取整到像素）
adv = {c: (font.adv[font.gid(c)] + 8) >> 4 for c in '0123456789:'}
# 生成 <span style="display:inline-block;width:43px">4</span> ...
```

这样整段文字的**总宽就与设备完全一致**，秒应当落在哪里一目了然。
字形自身的间距仍是浏览器渲染的，看位置关系足够。

（`/tmp/mock/gap.html` 就是这么做的：三个方案 x 两个时刻并排，
一眼看出"现状"在 `04:44` 时把秒压住了。）

## 六、什么时候该画原型

| 该画 | 不必画 |
|---|---|
| 改动版面结构（加减元素、调整位置） | 改一行颜色常量 |
| 挑选配色、对比度、文字层次 | 修一个明确的功能 bug |
| 两个以上方案需要比较 | 改动只影响代码结构、不影响画面 |

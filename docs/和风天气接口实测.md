# 和风天气接口实测记录

本文记录 dida-clock 实际调用的 4 个和风天气端点，以及它们的**真实请求与响应样本**。

## 这份文档的性质

- 样本由本项目**真实发请求抓取**，不是照抄官方文档，也不是手写示例。
- 手写样本容易"刚好符合实现假设"；真实数据能暴露想当然的地方 —— 这一点已经**两次**
  被证实（见下方"真实数据暴露过的问题"）。
- **凭据不入库**：`key` 与账号专属 host 一律用占位符。真实值在
  `main/include/weather_config_local.h`（被 `.gitignore` 忽略）。

## 凭据与 host 从哪来

| 项 | 位置 | 说明 |
|---|---|---|
| `QWEATHER_API_BASE_URL` | `main/include/weather_config_local.h` | 形如 `https://<你的账号>.re.qweatherapi.com`，**按账号分配**，不是公共域名 |
| `QWEATHER_API_KEY` | 同上 | 32 位十六进制 |
| 模板 | `main/include/weather_config_local.example.h` | 只含占位符，可提交 |

> 账号专属 host（`*.re.qweatherapi.com`）是付费版 API Host。免费版用的是
> `devapi.qweather.com`，**响应格式可能与本文不同** —— 换 host 后需重新验证。

## 共同约定

### 响应一律 gzip

**和风天气无条件返回 gzip**，即使请求里不发 `Accept-Encoding`：

```
content-encoding: gzip
```

而且它**不是标准 gzip 容器**意义上的压缩流起始 —— `tinfl` 一类只认裸 deflate 的
解压器不能直接用，必须先自行剥掉 gzip 头。本项目为此写了
`decompress::GzipDeflateOffset()`，用真实响应验证过（见"验证方式"）。

### 业务码 `code` 字段

`/geo/...`、`/v7/...` 三个端点在响应体里带 `"code": "200"` 表示业务成功。
**但 `/airquality/v1/...` 没有 `code` 字段** —— 对全部端点做统一业务码校验会
误杀所有合法的空气质量响应。解析器为此分成按端点区分的校验策略。

### 请求构造

4 个 URL 的拼法见 `components/weather/weather_api.cpp`，`key` 走 `UrlEncode`
（`quote_plus`，空格转 `+`，中文逐字节百分号编码）。

## 错误响应

和风天气的错误体是 **RFC 9457（problem details）风格**，与成功响应**结构完全不同**：

**请求**（故意用一个不存在的 location id）

```http
GET /v7/weather/now?key=<API_KEY>&location=999999999
```

**真实响应**

```http
HTTP/1.1 400
```

```json
{
  "error": {
    "status": 400,
    "type": "https://dev.qweather.com/docs/resource/error-code/#data-not-available",
    "title": "Data Not Available",
    "detail": "Data for this location is temporarily unavailable, please try another location."
  }
}
```

要点：

- **HTTP 状态码就是 400**，不是"HTTP 200 + 业务码非 200"。
- 响应体里**没有 `code` 字段**，只有 `error` 对象。
- `error.title` 与 `error.detail` 是**给人看的原因**。

### 我们当前的处理

`WeatherSync::FetchJson()` 在 `!response.IsHttpOk()` 时**直接返回失败，不解析响应体**：

```
失败原因 = "http_status: 400"
```

所以设备上会显示 `http_status: 400`（HTTP 层直接判失败，不进解析器）。

**已知不足**：`error.title`（如 `"Data Not Available"`）和 `error.detail`
（如 `"Data for this location is temporarily unavailable..."`）**被丢弃了**。
用户只能看到一个状态码，无法判断是"该位置暂无数据"还是"参数写错了"还是"额度用尽"。

**可改进方向**：非 2xx 时也解压并尝试读取 `error.title` / `error.detail`，把它们拼进
失败原因。这与 CONVENTIONS §7"同步状态要携带原因"一致。

> 本条是**静态查证发现的**，尚未实机验证；也还未改动代码。

## 与官方文档的对照（2026-09 核对）

对照 `dev.qweather.com/docs/` 的现行文档后，发现下面几处**必须知道**的差异。

### 一致的部分 ✓

| 项 | 官方文档 | 我们的实测 |
|---|---|---|
| Gzip | 「和风天气的 API **默认采用 Gzip** 进行压缩」 | 4 个端点全部 gzip |
| API Host | 「对每个开发者帐号都是独立、唯一的」 | `kq…re.qweatherapi.com` |
| 错误格式 | `HTTP 400` + `application/problem+json` + `{"error":{...}}` | 逐字段一致 |
| 城市查询路径 | `GET /geo/v2/city/lookup` | 一致 |
| 空气质量路径 | `GET /airquality/v1/current/{latitude}/{longitude}` | 一致 |

> **API Host 本身也是凭据的一部分**：官方原文「API Host 也是身份认证的一部分，这意味着
> 即使开发者的凭据泄露了，盗用者如果不知道 API Host 也是无法请求数据的」。
> 所以 host 与 key 一样**不应提交**（本项目两者都在 gitignore 的文件里）。
>
> 另：官方称原公共地址（`devapi.qweather.com` 等）**将从 2026 年起逐步停止服务**。

### ⚠ 实况天气与逐日预报：官方路径已经变了

**这是本次核对最重要的发现。**

| 我们在用的（旧） | 现行文档（新） |
|---|---|
| `GET /v7/weather/now?location={id}` | `GET /weather/v1/current/{latitude}/{longitude}` |
| `GET /v7/weather/7d?location={id}` | `GET /weather/v1/daily/{latitude}/{longitude}` |

- 现行文档里 **`/v7` 出现 0 次**。
- 但**旧路径目前仍然返回 200** 且数据正确（本文样本就是证据），所以尚未失效。
- 官方为这种情况准备了专门的错误码：**`DEPRECATED`，HTTP 403** ——
  「当前你请求的 API 已经弃用，请在开发文档中查找并使用最新版本」。
  也就是说**弃用是通过运行期 403 通知的，不是靠文档**。

**新版响应的结构与单位都不同**，不是换个 URL 就行：

| 我们页面要的 | 旧 `/v7/weather/now` | 新 `/weather/v1/current` |
|---|---|---|
| 天气文字 | `now.text` = `"雾"` | `condition.text` = `"小雨"` |
| 温度 | `now.temp` = `"24"`（字符串整数） | `temperature.value` = `24.28`（**浮点**） |
| 体感 | `now.feelsLike` = `"24"` | `feelsLike.value` = `26.11`（浮点） |
| 湿度 | `now.humidity` = `"95"`（**百分比**） | `humidity` = `0.95`（**0–1 小数**） |
| 风向 | `now.windDir` = `"东北风"` | `wind.direction.compass` = `"ne"`（**英文缩写**）+ `degree` = 46 |
| 风力 | `now.windScale` = `"3"` | `wind.scale` = 2 |
| 能见度 | `now.vis` = `"10"`（**公里**） | `visibility.value` = `9960`，unit `m`（**米**） |
| 图标 | `now.icon` = `"501"` | `condition.code` = `"305"` |

逐日预报同理：旧的是 `daily[]`（`fxDate`/`tempMax`/`textDay`…），
新的是 `days[]`（`forecastStartTime`/`temperatureMax`/`daytime`/`nighttime`…）。

**迁移的连带影响**：新 API 用 **经纬度**而不是 location id，所以
「城市查询 → 取 id → 查天气」会变成「城市查询 → 取经纬度 → 查天气」，
`location_id` 对天气端点不再必要（城市查询本身仍可用）。

**迁移成本**：改 2 个 URL + 重写 2 个解析器（含单位换算与风向映射表）+
新 fixture + 新测试。

### ⚠ 官方明确警告：不要放任错误继续发生

错误码文档原文：

> 注意：你应该妥善的处理遇到的错误，当错误发生时，请暂停请求并进行排查。
> **你不应该放任错误的继续发生，否则这些错误的请求看起来是一种 DDoS 攻击，
> 极端情况下，我们的安全策略可能冻结你的帐号。**

**我们当前的设计正撞这条**：

| 任务 | 周期 | 失败后 |
|---|---|---|
| `weather_now` | 30 分钟 | 下个周期照常重试 |
| `air_quality` | 60 分钟 | 同上 |
| `weather_7d` | 6 小时 | 同上 |

即约 **76 次/天**，且**没有任何退避、熔断或"永久错误就停"的判断**。
如果 key 失效（401）或额度耗尽（403），设备会**无限期地继续发失败请求**。

**可改进方向**：区分**永久性错误**与**瞬时错误** ——

- 永久：401 UNAUTHORIZED、403 NO CREDIT、403 DEPRECATED、403 FORBIDDEN
  → 停止该端点的周期请求（或退避到很长），并把明确原因带到调用方
- 瞬时：网络超时、DNS 失败、5xx → 保持现有重试

### 我们遗漏的错误码分类

官方列出的错误码（我们目前**全部丢弃**，只留一个 `http_status: N`）：

| HTTP | 名称 | 含义 |
|---|---|---|
| 400 | INVALID PARAMETER | 参数值错误，响应里带 `error.invalidParams` |
| 400 | MISSING PARAMETER | 必选参数缺失，同样带 `invalidParams` |
| 400 | NO SUCH LOCATION | 地点不存在或 Location ID 错误 |
| 400 | DATA NOT AVAILABLE | 该位置暂无数据（**本文抓到的就是这条**） |
| 401 | UNAUTHORIZED | 鉴权失败；官方出于安全**不返回具体原因** |
| 403 | NO CREDIT | 额度不足 |
| 403 | DEPRECATED | **API 已弃用** ← 旧 `/v7` 若被下线会走这条 |
| 403 | FORBIDDEN | 禁止访问 |
| 402 | （订阅超限） | 包年包月当月请求量超限 |

响应里的可选字段 `error.invalidParams` 是一个字符串数组，指出具体哪个参数有问题。

### 一处措辞更正

本文上一版把「空气质量没有顶层 `code` 字段」列为"真实数据暴露的问题"。
更准确的说法是：**官方文档明确显示该响应没有顶层 `code`**（`code` 只出现在
`indexes[]`/`pollutants[]` 内部，如 `"pm2p5"`、`"us-epa"`）。

所以它是**我们自己没细读文档导致的实现陷阱**，而不是文档缺失。真实响应把它暴露出来，
但读文档本可以避免 —— 这条记录保留，措辞已更正。
